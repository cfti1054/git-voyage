# git-voyage 개발 오케스트레이터

설계 → 구현 → 검증 → 보고 순서로 작업을 조율한다. 실행 방식은 **서브에이전트 위임**이다. 각 단계에서 `Agent` 도구로 전문 에이전트를 호출하고, 결과는 `_workspace/`에 남긴다.

## 에이전트 구성

| 에이전트 | 모델 | 역할 | 수정 권한 |
| --- | --- | --- | --- |
| `architect` | opus | 요청 분석, 영향 파일과 구현 순서 설계 | 없음 (읽기 전용) |
| `scene-dev` | opus | 3D 씬, 건물, 비행, 카메라, 터치 | 있음 |
| `data-dev` | sonnet | GitHub 데이터, API 라우트, 캐시, 타입 | 있음 |
| `asset-dev` | opus | Blender MCP로 glb 건물·공원 모델 제작, 내보내기 | 있음 (`public/models/`만) |
| `qa-reviewer` | opus | tsc·lint·build 실행, glb 참조 확인, 계획 대비 검토 | 없음 (읽기 전용) |

모델은 작업의 성격으로 골랐다. 설계, 3D 코드 생성, 교차 검증처럼 깊은 추론이 필요한 일에는 opus를 쓰고, 정해진 절차의 API 작업에는 sonnet을 썼다.

규칙과 상수는 `voyage-conventions` 스킬을 따른다. 모든 에이전트가 작업 전에 이 스킬을 읽는다.

## 0단계: 현재 상태 확인

1. `_workspace/`가 있는지 확인한다.
   - 없으면 새로 실행한다.
   - 있고 일부만 고쳐 달라는 요청이면 해당 단계나 에이전트만 다시 실행한다.
   - 있고 새 요청이면 `_workspace/`를 `_workspace_{YYYYMMDD_HHMMSS}/`로 옮긴 뒤 새로 실행한다.
2. `git status`로 작업 트리 상태를 확인한다. 사용자의 진행 중 변경이 있으면 덮어쓰지 않도록 먼저 알린다.

## 1단계: 설계

`architect`를 호출한다. 전달할 것은 사용자 요청 원문과 관련 파일 힌트다.

- 결과를 `_workspace/01_architect_plan.md`에 저장한다.
- 계획에 "확인 필요" 항목이 있으면 사용자에게 질문하고 멈춘다. 추측으로 진행하지 않는다.
- 계획이 명확하면 바로 2단계로 간다.

## 2단계: 구현

계획의 담당 항목에 따라 호출한다.

- 3D 씬 변경은 `scene-dev`에게 전달한다.
- 데이터 변경은 `data-dev`에게 전달한다.
- glb 모델을 새로 만들거나 고치는 작업은 `asset-dev`에게 먼저 전달한다. 로딩 경로를 바꾸는 코드 작업은 그 뒤 `scene-dev`가 맡는다.
- 두 작업이 독립이면 한 메시지에서 두 에이전트를 **병렬**로 호출한다.
- 의존하면 앞 작업을 끝낸 뒤 호출한다. 예: 응답 필드를 바꾸는 `data-dev` 작업이 먼저, 그 필드를 쓰는 `scene-dev` 작업이 다음이다.

각 에이전트에게는 다음을 함께 전달한다.
- 설계 계획 중 자기 담당 부분
- 변경 대상 파일 경로
- 완료 후 보고 형식 (변경 파일, `tsc` 결과, 확인 못 한 부분)

구현 결과는 `_workspace/02_{agent}_impl.md`에 저장한다.

## 3단계: 검증

`qa-reviewer`를 호출한다. 전달할 것은 변경 파일 목록과 설계자의 검증 포인트다.

- 결과를 `_workspace/03_qa_report.md`에 저장한다.
- **통과**면 4단계로 간다.
- **수정 필요**면 발견 사항을 담당 에이전트별로 나눠 해당 에이전트에게 다시 보낸다. 수정 후 QA를 다시 호출한다.
- 같은 항목이 두 번 연속 실패하면 자동 수정을 멈추고 사용자에게 보고한다.

## 4단계: 보고

최종 응답에 다음을 포함한다.

- 요청 요약과 선택한 해석 (요청을 어떻게 이해했는지)
- 변경 파일 목록
- QA 결과 (tsc, lint, build 각각의 실제 결과)
- 확인하지 못한 부분 (예: 실제 GitHub 토큰으로 조회, 브라우저에서 비행 감각)
- 커밋이 필요하면 `voyage-conventions`의 커밋 형식을 제안한다. 커밋과 푸시는 사용자가 요청할 때만 한다.

## 오류 처리

- 에이전트 응답이 없거나 실패하면 한 번 다시 호출한다. 또 실패하면 `_workspace/`에 실패 기록을 남기고 사용자에게 알린다.
- 사용량 한도, 인증 만료, 권한 거부는 다시 시도하지 않는다. 부분 산출물을 직접 열어 어디까지 진행됐는지 확인하고, 누락된 내용을 사용자에게 보고한다.
- 빈 결과를 추측으로 채우지 않는다. 에이전트가 확인하지 못한 사실은 "확인 안 됨"으로 남긴다.
- `npm run build`가 실패하면 QA에 원인을 넘기고, 원인이 명확할 때만 수정한다.

## 테스트 시나리오

**정상 흐름:** "건물 높이 상한을 200으로 올려줘"
1. `architect`가 `city.ts`의 `MAX_HEIGHT`와 충돌 상자 영향을 계획한다.
2. `scene-dev`가 상수와 관련 코드를 고친다. `data-dev`는 필요 없으므로 호출하지 않는다.
3. `qa-reviewer`가 tsc, lint, build를 실행하고 충돌 경계가 맞는지 확인한다.
4. 보고서에 변경 파일과 QA 결과를 담는다.

**오류 흐름:** "커밋 내용 API 응답 형식을 바꿔줘"
1. `architect`가 `data-dev`와 `scene-dev` 모두 영향을 받는다고 계획한다.
2. `data-dev`가 먼저 응답 형식을 바꾸고, 변경된 필드를 보고한다.
3. `scene-dev`는 `VoyageApp.tsx`의 소비 코드가 맞는지 확인한다. 맞지 않으면 계획에 없던 파일을 건드리기 전에 사용자에게 묻는다.
4. QA가 타입 오류를 발견하면 담당 에이전트에게 돌려보내고, 두 번 실패하면 사용자에게 보고한다.

## 후속 요청 처리

"다시 실행", "재검증", "보완", "이전 결과 기반으로 수정"처럼 말하면 0단계로 돌아가 `_workspace/`를 확인한다. 전체를 다시 하지 않고 필요한 단계만 실행한다.
